**版本**：v1.1  
**日期**：2026-06-11  
**适用平台**：Windows 10/11（仅PC桌面端）

### 第一部分 项目概述
#### 1.1 项目背景与目标
构建一款运行于Windows PC的智能AI桌面宠物（桌宠），以拟人化猫系角色为载体，提供**长期记忆与个性化对话**、**智能日程提醒**、**健康管理**、**联网搜索**、**LBS附近店铺推荐**等能力。所有AI能力本地运行，追求极低金钱成本，仅内测自用。
#### 1.2 项目范围
- **目标用户**：个人内测使用，不做公开发行。
- **平台限制**：仅Windows 10/11 x64，不做跨端。
- **金钱成本**：年度支出0~50元，仅Azure Bing API可能产生微量费用。
- **数据隐私**：全本地存储加密，语音/图像/位置数据不外传。
#### 1.3 核心特性一览
| 特性 | 说明 |
|------|------|
| 本地大语言模型 | Ollama + Qwen2.5-7B量化，RTX 4060 GPU推理 |
| 长期记忆 | FAISS向量库 + SQLite加密，支持遗忘与置信度 |
| 日程管理 | 自然语言/OCR长文本/图片批量导入，双阶段提醒 |
| 健康管理 | 饮食推荐、饮水/久坐/用眼提醒、作息与情绪跟踪 |
| LBS推荐 | 高德API附近餐饮搜索，结合用户偏好与天气 |
| 联网搜索 | Bing API免费层 + 本地DuckDuckGo备用 |
| 桌面交互 | 悬浮猫系角色 + 对话气泡，纯静音，无语音干扰 |
| 自动更新 | 从GitHub Release拉取最新版本 |

### 第五部分 业务逻辑设计
#### 5.1 系统核心状态机
系统维护两个相互关联的状态机：**用户活动状态** 与 **桌宠行为模式**。
##### 5.1.1 用户活动状态
| 状态 | 判定条件 | 优先级 |
|------|---------|--------|
| `active` | 检测到键鼠操作，且非全屏 | 正常 |
| `idle` | 连续无操作超过5分钟（可配置） | 正常 |
| `busy` | 当前有全屏应用运行 | 高 |
| `sleep` | 根据作息推测在睡眠时段 | 高 |
| `away` | 系统锁屏或长时间无任何活动 | 中 |
状态转换规则：
- `active` → `idle`：空闲计时器到期。
- `idle` → `active`：检测到任意键鼠事件。
- `active`/`idle` → `busy`：检测到全屏窗口（通过Win32 API获取前台窗口状态）。
- `busy` → `active`：全屏窗口关闭或最小化。
- 任何状态 → `sleep`：进入预设的睡眠时段（如23:00-07:00），且无用户交互。
- 任何状态 → `away`：系统锁屏事件。
##### 5.1.2 桌宠行为模式
| 模式 | 说明 | 触发条件 |
|------|------|---------|
| `companion` | 陪伴模式，轻量互动 | 用户状态为`active` |
| `caretaker` | 关怀模式，主动推送健康建议 | 用户状态为`idle`，或定时器到期（饭点、喝水）且状态非`busy`/`sleep` |
| `alarm` | 通知模式，日程强提醒 | 日程提醒时间到达，无视用户状态（除非`silent`） |
| `silent` | 静默模式，仅托盘，不弹任何通知 | 用户手动开启免打扰时段，或状态为`busy`/`sleep`时自动进入 |
模式切换矩阵：
| 当前模式 | 触发事件 | 目标模式 |
|----------|---------|----------|
| `companion` | 用户进入`idle` | `caretaker` |
| `companion` | 用户进入`busy` | `silent`（自动） |
| `caretaker` | 用户恢复`active` | `companion` |
| `caretaker` | 用户进入`busy` | `silent` |
| `silent` | 免打扰时段结束/用户恢复`active` | `companion` |
| 任何 | 日程提醒触发 | `alarm`（临时，完成后返回原模式） |
| 任何 | 用户手动切换免打扰 | `silent` |

当多个提醒同时触发时，由 `NotificationManager` 统一管理显示队列。优先级：**到期强提醒 > 提前预警 > 健康提醒**。高优先级提醒可打断当前显示，当前提醒自动暂存为"稍后"；用户操作中或锁定3秒内不可打断。最多小睡3次，超出后自动标记为"已错过"。

#### 5.2 健康管理引擎流程
##### 5.2.1 饮食推荐决策流
1. **触发**：当前时间进入饭点区间（默认午餐11:30-12:30，晚餐17:30-18:30），且用户状态非`busy`/`sleep`，且当日该餐次未推荐过或用户未标记已吃。
2. **上下文收集**：
   - 从`user_profile`读取固定偏好、忌口。
   - 从`user_traits`读取近期习得偏好。
   - 从`meal_log`读取过去3天饮食记录。
   - 从`mood_snapshot`取最新情绪。
   - 调用LBS服务获取当前位置及附近餐饮店铺。
   - 调用联网搜索获取天气。
3. **生成推荐**：拼接提示词，调用LLM生成推荐文案（含自制建议、店铺推荐、健康小贴士）。
4. **气泡呈现**：桌宠动作（敲屏）+ 气泡显示推荐，提供按钮【就吃这个】【换一个】【已吃过】。
5. **反馈处理**：
   - 确认：记录至`meal_log`，偏好置信度+1。
   - 换一个：重新调用LLM（附加条件"不要重复上一个建议"），最多3次。
   - 已吃过：记录并询问吃了什么（可选输入）。
   - 忽略：1小时后重试一次，仍忽略则当日不再打扰。
##### 5.2.2 饮水提醒逻辑
- **间隔计时器**：默认45分钟（可配置），仅在工作时段（默认9:00-21:00）计时。
- **触发条件**：计时器到期，且用户状态非`busy`/`sleep`/`silent`。
- **动作**：桌宠敲屏+气泡"该喝水啦！今日已饮X ml，还差Y ml"。
- **反馈**：用户点击【喝啦】记录250ml；【跳过】推迟15分钟；无操作3秒后消失，15分钟后再提醒。
- **日终检查**：21:00计算日总量，若低于目标（默认2000ml），温柔提醒一次。
##### 5.2.3 久坐/活动提醒
- **连续活动监控**：记录最后一次键鼠操作时间，计算连续活动时长（中间若有超过30秒停顿则重置）。
- **触发阈值**：连续活动超过50分钟（动态调整），且非全屏，且未处于`sleep`/`silent`。
- **动态阈值调节公式**：基于最近5次提醒的反馈计算拒绝率。若拒绝率 > 60%，阈值+10分钟（上限90分钟）；若接受率 > 80%，阈值-5分钟（下限30分钟）。每周一凌晨重置为默认值（50分钟）。
- **动作**：桌宠敲屏+气泡"已经工作50分钟啦，起来活动一下？"，随机建议一种活动（眼保健操/拉伸/走动）。
- **活动引导**：用户选择休息后，气泡切换为简易活动指导（文字+计时3分钟），桌宠做打哈欠/伸懒腰动画。
- **拒绝处理**：用户点【忽略】后，阈值暂时+10分钟（最多90分钟），避免骚扰。
##### 5.2.4 作息分析
- **采集**：每日记录首次和最后一次交互时间戳。
- **推测规则**：末次交互后若持续30分钟无操作，记录为`sleep_candidate`；首次交互为`wake_candidate`。
- **分析**：每7天计算平均入睡/起床时间及标准差。若标准差>2小时，判定为不规律。
- **干预**：连续7天睡眠<6小时或极度不规律时，在早晨问候中温和提醒"最近睡得有点晚哦，今天早点休息吧"。
##### 5.2.5 情绪日志
- **采集时机**：每次用户发送消息后。
- **分析**：调用本地轻量情感模型（DistilBERT微调），输出标签`positive`/`neutral`/`negative`及强度。
- **存储**：写入`mood_snapshot`表。
- **趋势检测**：连续两次`negative`时，在回复中加入关怀语句；每周生成情绪曲线（设置面板展示）。

#### 5.3 日程提醒调度流程
##### 5.3.1 创建流程
```
用户输入 → 判断输入类型：
  文字 → 单句解析器（dateparser+LLM兜底）
  长文本 → 分句 → 逐句LLM判断是否含日程
  图片 → PaddleOCR提取文字 → 同长文本处理
→ 输出结构化日程列表 → 冲突检测（查询同时间段已有日程）
→ 如有冲突弹出警告 → 用户确认后批量写入schedule表
→ 计算提醒时间并注册到APScheduler
```
##### 5.3.2 提醒触发
- **提前提醒**：在`start_time - reminder_offset_min`时触发，桌宠动作+气泡显示"X分钟后：{标题}"，可【了解详情】【推迟5分钟】。
- **到期提醒**：到达`start_time`时，若状态仍为`active`，触发强提醒：桌宠持续敲屏+气泡显示标题和时间，直到用户【完成】或【小睡】（默认5分钟，可多次）。
- **错过处理**：若超过结束时间24小时未标记，自动标记为`missed`。
##### 5.3.3 重复日程实例生成
- 采用RFC 5545规则解析，生成未来3个月的具体实例存入`schedule_instance`表。
- 每周日凌晨补充新实例（保持未来3个月窗口）。
- 修改单个实例时可断开与系列的链接，成为例外。
##### 5.3.4 提醒偏移学习
- 记录用户对提醒的反馈序列（推迟次数、间隔）。
- 若某类型日程（如"会议"）连续3次被用户推迟，该类型默认偏移量+5分钟，上限60分钟。
- 存储在`user_traits`中，键如`reminder_offset_meeting`。

#### 5.4 个性化信息抽取与遗忘机制
##### 5.4.1 信息抽取流水线
1. **规则匹配层**：识别明确偏好陈述（"我喜欢/讨厌..."），直接抽取为待确认特质。
2. **情感标记层**：对每条用户消息进行情感分析，若强度>0.7，标记为潜在情绪记忆。
3. **LLM摘要层**：每累积50轮对话，调用LLM生成对话摘要，提取新出现的偏好、习惯、重要事件，生成候选特质和情节记忆。
4. **置信度计算**：
   - 用户显式输入的偏好 `confidence=1.0`
   - LLM提取的偏好 `confidence=0.6`（首次），每重复出现一次+0.1，上限0.9
   - 情节记忆的重要性由情感强度和对话上下文判定（1-10）
##### 5.4.2 遗忘算法
- **情节记忆衰减**：
  - 每条记忆初始重要性为`s`（1-10），半衰期T默认30天（重要事件可设90天）。
  - 当前分数 = s × exp(-ln(2) × Δt / T)
  - 分数<1时移入归档表，不参与日常检索。
- **特质遗忘**：
  - 若特质90天内`last_active`未更新且`occurrences<3`，自动删除。
  - 用户主动修改偏好时，旧相关特质置信度直接降为0.1并标记待删除。
- **手动遗忘**：提供"忘记我"按钮，一键清除所有画像、记忆、日志。

#### 5.5 搜索多级降级链
```
用户搜索意图 → 检查缓存（30分钟有效）
  ↓ 未命中
尝试 Azure Bing API (超时5秒)
  ↓ 失败/超时
尝试本地 SearXNG (Docker, 超时5秒)
  ↓ 失败/未部署
降级 DuckDuckGo HTML抓取
  ↓ 失败
返回"搜索服务暂不可用"，缓存空结果5分钟
```
- 每个源返回结果后进行质量检查：至少包含2条非空摘要，否则视为失败。
- 所有降级过程记录日志，UI仅显示"搜索遇到点问题，正在尝试备用通道"或最终失败提示。

**API 用量统计**：每次成功调用高德/Bing API 后，在 `app_settings` 表中更新当日/当月计数器。设置面板可查看剩余次数。
**近限额保护**：
- 高德：当日调用 ≥ 4500次 → 自动关闭周边搜索，饮食推荐仅提供自制建议。
- Bing：当月调用 ≥ 900次 → 强制切换 DuckDuckGo 通道。

#### 5.6 模块间通信与事件总线设计
##### 5.6.1 事件总线架构
采用**发布-订阅模式**，核心组件 `EventBus` 维护事件队列和订阅者映射。

EventBus 提供三种订阅模式：
- `subscribe_sync`：回调在发布线程同步执行（仅适用于纯数据操作）。
- `subscribe_async`：回调在线程池异步执行（适用于耗时操作）。
- `subscribe_ui`：回调通过 Qt 信号槽在主线程执行（所有 UI 更新必须使用此模式）。

实现：EventBus 内部持有一个 `QObject` 子类 `UiSignals`，为每种 UI 事件定义 `pyqtSignal`。`subscribe_ui` 的回调函数注册为信号的槽，确保线程安全。

**主要事件及流向：**
| 事件类型 | 发布者 | 订阅者 | 用途 |
|---------|--------|--------|------|
| `SCHEDULE_ALERT` | 日程调度器 | 通知控制器、UI动画 | 触发提醒动作 |
| `HEALTH_REMINDER` | 健康引擎 | 通知控制器、UI动画 | 饮食/饮水/活动提示 |
| `USER_ACTIVITY_CHANGE` | 空闲检测器 | 模式管理器、动画控制器 | 切换陪伴/关怀模式 |
| `MOOD_DETECTED` | 对话管理 | 健康引擎、个性化引擎 | 情绪记录与分析 |
| `MEMORY_CREATED` | 记忆管理 | 个性化引擎 | 触发画像更新 |
| `PREFERENCE_UPDATED` | 个性化引擎 | 推荐引擎 | 饮食/日程偏好变更 |
| `SYSTEM_STATUS` | 各服务 | UI状态栏 | 模型加载/错误状态 |
| `UI_ACTION` | UI层 | 各业务模块 | 用户操作转发 |
| `EXIT_REQUEST` | 托盘菜单 | 所有模块 | 优雅退出 |
##### 5.6.2 同步服务调用
对于需要即时返回值的操作（如获取位置、读取用户画像），通过`ServiceRegistry`获取服务实例直接调用，返回`Result`对象。
##### 5.6.3 全局状态管理
`StateManager` 维护：
- 当前用户活动状态
- 当前桌宠行为模式
- 免打扰时段配置
- 系统全局设置（通知开关等）
各模块可读取状态，重要状态变更通过事件发布通知。

#### 5.7 容错与故障恢复设计
- **LLM调用失败**：连续3次失败→切换预设回复库，托盘图标变灰提示"AI降级模式"，日程提醒等功能保持正常。
- **数据库损坏**：启动时检测 SQLite 完整性（`PRAGMA integrity_check`），异常时从最近备份恢复或新建空库并通知用户。
- **模型加载超时**：设置30秒超时，超时后跳过该模型（如STT），仅提供文字输入。
- **网络中断**：搜索、LBS 自动降级，上次成功缓存延长有效期。
- **主进程守护**：另开 watchdog 线程监控主循环心跳，若卡死超过30秒，自动重启程序（可配置开关）。

#### 7.6 用户引导流程
首次启动时，触发5步引导向导（模态对话框，700×500px，暖色背景，猫咪在旁边陪伴）：
**第1步：欢迎**
- 猫咪做欢迎动画（伸懒腰+端正坐好）。
- 文字："你好！我是你的桌面伙伴，一只喜欢打瞌睡的猫咪~ 先让我了解你一下吧！"
**第2步：基础信息**
- 昵称输入框（跳过时填写"用户"）。
- 饮食偏好：多选按钮（辣/清淡/西式/日料/甜食）+ 忌口输入框（跳过时均为空列表）。
- 作息类型：早鸟/夜猫/不规律（单选，跳过时默认"不规律"）。
- 向导完成时提示"可随时在设置中修改"。
**第3步：功能初体验**
- 文字："试试看，对我说'提醒我10分钟后喝水'"
- 输入框模拟对话，成功创建后猫咪给出开心反馈（眯眼摇尾）。
- 提示："所有提醒我都会轻轻敲屏幕告诉你，不会发出声音打扰你"
**第4步：健康设置**
- 久坐提醒间隔滑块（30-90分钟，默认50）。
- 饮水提醒间隔滑块（30-60分钟，默认45）。
- 可勾选"暂时跳过，以后再设"。
**第5步：完成**
- 猫咪抱着抱枕出现。
- 文字："都设置好啦！我平时会在这里（指向右下角）打瞌睡，想我了就点我一下。所有数据都在你的电脑上，绝对安全。"
- 按钮：【开始使用】（关闭向导，猫咪进入待机动画）。
**向导特性**：
- 每步有"上一步"和"跳过"按钮，不强制完成。
- 进度条显示当前步骤（如 2/5）。
- 完成后将数据写入`user_profile`和`app_settings`。

### 第九部分 核心注意点与难点
#### 9.1 模型显存管理与动态调度
**难点描述**：
RTX 4060仅有8GB显存，需同时（或分时）承载LLM（Qwen2.5-7B-GPTQ，约4-5GB）、语音识别（faster-whisper-large-v3，约2GB）、OCR（PaddleOCR GPU，约1-2GB）三个大模型。若同时加载，显存必然溢出。
**核心策略——按需加载+显存监控**：
| 模型 | 加载时机 | 卸载时机 | 显存占用 |
|------|---------|---------|---------|
| LLM | 程序启动，常驻 | 永不卸载（除非降级模式） | 4-5GB |
| faster-whisper | 用户点击语音按钮或唤醒词触发 | 识别完成后闲置5秒 | 2GB |
| PaddleOCR | 用户粘贴/拖入图片时 | OCR完成后闲置10秒 | 1-2GB |
**实现要点**：
1. **显存水位监控**：通过`nvidia-smi`或`pynvml`库实时获取可用显存。阈值设为800MB安全线，低于此值拒绝加载新模型。
2. **LLM推理挂起**：加载STT或OCR前，通过信号量暂停LLM推理线程（不卸载模型，仅暂停GPU计算），释放部分显存给新模型。
3. **加载动画**：模型加载期间，需通过 EventBus 的 `subscribe_ui` 更新状态指示器，确保 UI 线程安全。猫咪显示"思考中"动画+气泡文字"正在听..."（STT）或"正在看图片..."（OCR），避免用户重复点击。
4. **降级预案**：若显存持续不足（如后台有游戏占用），自动切换LLM为CPU推理（Ollama配置切换），牺牲速度保稳定性。
**注意**：faster-whisper加载时需指定`device="cuda"`和`compute_type="float16"`以最小化显存占用。

#### 9.2 OCR识别准确率保障
**难点描述**：
用户上传的截图可能背景复杂、文字歪斜、字体花哨、分辨率低，直接送入OCR识别率堪忧。日程抓取依赖OCR结果，错误会导致漏提醒或错误提醒。
**核心策略——预处理管道+双引擎兜底**：
**预处理管道（顺序执行）**：
1. **格式归一化**：统一转换为PNG无损格式，确保后续处理兼容。
2. **灰度化**：将彩色图像转为灰度，减少背景干扰。
3. **自适应直方图均衡化（CLAHE）**：增强对比度，使文字更突出（可选，默认关闭）。
4. **透视校正**：检测文本区域是否倾斜（通过轮廓检测+最小外接矩形），若倾斜角>5°则自动旋转校正（可选，默认关闭）。
5. **降噪**：中值滤波去除椒盐噪声（截图常见）。
6. **分辨率检查**：若图片DPI < 150，使用超分辨率模型（可选轻量ESPCN）放大1.5-2倍（可选，默认关闭）。

Alpha 版仅使用灰度化+等比缩放+PaddleOCR。

**双引擎识别**：
- 主引擎：PaddleOCR（GPU），配置中文+英文语言，启用文本方向检测。
- 兜底引擎：Tesseract OCR，配置`chi_sim+eng`语言包。
- 当PaddleOCR返回的文本置信度均值 < 0.7时，自动切换Tesseract。
- 两者均失败则提示用户"图片文字不清晰，建议粘贴纯文本或重新截图"。
**后续处理**：
- 识别出的文本按行合并，去除多余空格/换行。
- 若文本长度 > 50字，分句后批量送入LLM解析日程，输出JSON列表。
**注意**：PaddleOCR首次加载会下载模型，需在阶段0验证网络畅通并缓存到本地目录。

#### 9.3 多提醒任务不丢失与恢复
**难点描述**：
提醒功能是桌宠的核心价值。若程序崩溃、电脑重启或意外退出，所有未触发的提醒若丢失，用户体验将严重受损。
**核心策略——持久化+快照+恢复**：
1. **持久化存储**：
   - 所有提醒任务在创建时立即写入`schedule`表，状态为`active`。
   - APScheduler的任务队列基于数据库中的`active`日程动态构建。
2. **运行时快照**：
   - 每15分钟将APScheduler的内存队列、健康提醒倒计时状态序列化为JSON，写入`%APPDATA%/SmartDesktopPet/data/runtime_snapshot.json`。
   - 正常退出时（`EXIT_REQUEST`事件），立即保存一次快照。
3. **启动恢复**：
   - 程序启动时，首先检查`runtime_snapshot.json`：
     - 若存在且时间戳在上次退出后，加载快照重建调度器状态。
     - 若快照不存在或损坏，从`schedule`表重建：查询所有`status='active'`且`start_time > now()`的日程，批量注册到APScheduler。
   - 重建后立即触发一次检查，若有已过期但未标记完成的提醒（如崩溃发生在提醒瞬间），立即补发通知。
4. **健康提醒恢复**：
   - 饮水计时器、久坐计时器的剩余时间写入快照，恢复后继续计时。
   - 饭点推荐状态（今日是否已推荐）从`meal_log`表查询恢复。
**注意**：快照文件使用原子写入（先写临时文件，重命名覆盖），防止写入过程中崩溃导致文件损坏。

#### 9.4 个性化引擎的置信度控制
**难点描述**：
个性化若过于激进（单次对话就固化偏好），会导致错误画像；若过于保守，长期无个性化体验。需要在"快速学习"和"稳定准确"间平衡。
**核心策略——分层置信度+反馈衰减**：
**置信度体系**：
| 信息来源 | 初始置信度 | 增长规则 | 衰减规则 |
|---------|----------|---------|---------|
| 用户显式输入（设置/引导） | 1.0 | 不变 | 用户主动修改时才变 |
| 用户明确陈述（"我喜欢X"） | 0.85 | 同类陈述+0.05，上限0.95 | 90天无复现-0.1 |
| LLM抽取（对话隐含偏好） | 0.5 | 同类行为重现+0.1，上限0.8 | 60天无复现-0.15 |
| 系统推测（情绪关联） | 0.3 | 连续3次一致+0.2 | 30天无复现即删除 |
**关键规则**：
1. **三击确认**：LLM抽取的偏好需在3次不同对话中被重现（`occurrences >= 3`），且置信度>0.6，才注入个性化提示词。
2. **用户反馈优先**：用户每次对推荐说"换一个"或明确否定，相关特质置信度-0.2并记录否定证据。
3. **定期审计**：每周日凌晨对`user_traits`执行清理，删除置信度<0.3且超过60天未激活的特质。
4. **矛盾处理**：若新特质与旧高置信度特质冲突（如原先喜欢辣，新证据显示偏好清淡），将旧特质置信度-0.3，新特质从0.5开始累积。
**注意**：用户可随时在"记忆管理"界面查看、手动修改或删除任何特质，手动操作的优先级最高（置信度强制1.0且不上限衰减）。

#### 9.5 自动更新安全性与回滚
**难点描述**：
自动更新涉及下载外部文件并替换程序自身，若下载中断、文件损坏或被篡改，可能导致程序无法启动。
**核心策略——启动器模式+校验+原子替换+回滚**：

采用启动器模式（Updater.exe）。流程：下载新版本→用户确认→启动Updater→主程序退出→Updater替换文件→重启主程序。增加回滚：连续3次启动失败自动恢复上一版本。

1. **版本检查**：
   - 启动时请求GitHub API：`GET /repos/{owner}/{repo}/releases/latest`。
   - 对比`tag_name`与本地`update_info.current_version`。若相同则跳过。
2. **下载与校验**：
   - 下载更新包（如`SmartDesktopPet_v1.1.0.zip`）。
   - 校验：对比GitHub Release中附带的`sha256`与下载文件的本地计算值，不匹配则丢弃并重试一次，仍失败则报告用户。
3. **用户确认**：
   - 弹出更新确认对话框，显示版本号、更新内容、文件大小。
   - 用户确认后，启动独立的`Updater.exe`进程，主程序退出。
4. **原子替换**：
   - Updater将当前程序目录复制一份为`SmartDesktopPet_backup`（保留旧版本）。
   - 解压更新包到临时目录`SmartDesktopPet_new`。
   - 验证新版本可启动（静默启动→检查进程存在→退出），若失败则删除新目录，保留旧版本。
   - 验证通过后，用`SmartDesktopPet_new`替换主目录，删除旧备份，重启主程序。
5. **回滚机制**：
   - 设置面板提供"回滚到上一版本"按钮，从`SmartDesktopPet_backup`恢复。
   - 若更新后程序启动失败3次（通过启动计数文件检测），下次启动时自动恢复备份。
6. **更新频率控制**：
   - `update_info.last_check_time`记录上次检查时间，每日仅检查一次。
   - 用户可在设置中关闭自动检查，或手动点击"检查更新"。
**注意**：更新包托管在GitHub Releases，免费且稳定。若未来仓库设为Private，需配置Personal Access Token（仅读权限）。

#### 9.6 其他关键注意点
| 注意点 | 说明 |
|--------|------|
| **数据库WAL模式** | 启用 `PRAGMA journal_mode=WAL` 提升并发读取性能，写操作统一通过`db_queue`队列串行执行。 |
| **应用层加密字段** | 敏感字段的读写封装；DPAPI 密钥保护示例说明。 |
| **PyQt5线程安全** | UI操作必须在主线程执行。事件总线回调中若需更新UI，使用`QMetaObject.invokeMethod`或`pyqtSignal`跨线程调度。 |
| **全屏检测准确性** | 部分应用（如浏览器全屏视频）可能误判。通过Win32 API `GetWindowRect`和`GetForegroundWindow`获取窗口尺寸，与屏幕分辨率对比，允许±5%误差。 |
| **高德API配额** | 每日5000次对个人使用充裕，但仍需本地缓存（1小时）减少重复请求。API 限额临近时托盘气泡提示"本月搜索次数剩余XX"。若未来超量，可切换腾讯地图API（10000次/日免费）。 |
| **Ollama进程守护** | Ollama可能因异常崩溃。启动时检查进程是否存在，若不在则自动启动。LLM调用失败时先尝试重启Ollama（最多3次），再进入降级模式。 |
| **配置文件热更新** | 用户在设置面板修改参数后，通过`UI_ACTION`事件通知相关模块刷新配置，而非读文件轮询。 |

#### 11.4 常见环境问题排查
**Ollama GPU 不可用**：
1. 检查 NVIDIA 驱动版本 ≥ 535.x
2. 运行 `nvidia-smi` 确认 CUDA 版本 ≥ 12.1
3. 执行 `ollama info` 查看是否识别到 GPU
4. 若仍不可用，设置环境变量 `OLLAMA_LLM_LIBRARY="cuda"`
5. 重装 Ollama GPU 版本：`winget install Ollama.Ollama`

**PaddleOCR 安装失败**：
1. 确保 Python 版本为 3.8-3.11（3.12 暂不支持）
2. 先安装 PaddlePaddle：`pip install paddlepaddle-gpu==2.6.1 -i https://pypi.tuna.tsinghua.edu.cn/simple`
3. 再安装 PaddleOCR：`pip install paddleocr`
4. 若报错 "Microsoft Visual C++ Redistributable"，安装 VC++ 2015-2022 运行库

**PyQt5 线程报错**：
1. 所有 UI 更新必须在主线程执行
2. 使用 `pyqtSignal` 跨线程传递数据，不要直接操作控件
3. 事件总线 UI 回调必须使用 `subscribe_ui` 模式
4. 避免在定时器回调中直接修改 UI，通过信号中转

**FAISS 导入错误**：
1. Windows 下使用 `faiss-cpu` 而非 `faiss-gpu`
2. 执行 `pip install faiss-cpu --no-cache`
3. 若报错 DLL 缺失，安装 Visual C++ Redistributable

**模型下载慢**：
1. Ollama 模型：设置 `OLLAMA_HOST=http://127.0.0.1:11434` 后使用国内镜像
2. HuggingFace 模型：使用 `hf-mirror` 或 ModelScope 镜像
3. PaddleOCR 模型：手动下载到 `~/.paddleocr/whl/` 目录

**内存泄漏排查**：
1. 使用 `memory_profiler` 装饰关键函数
2. 检查 PyQt5 对象是否正确 `deleteLater()`
3. 确认 FAISS 索引定期重建而非无限追加
4. 检查事件总线订阅是否正确取消
