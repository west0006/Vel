## 一、诊断：为什么只有 idle 看得出来

### 1.1 实测数据（当前实现）

帧驱动：`ui/floating_pet.py:366` 的 `EMOTION_INTERVALS`（按情绪设间隔）+ `:505` 动态 `setInterval`。

| 情绪 | 帧数 | 帧间隔 | **一轮总时长** | 循环方式 | 观察 |
|---|---|---|---|---|---|
| idle | 4 | 150ms | **600ms** | 循环 | ✅ 呼吸感明显（用户确认） |
| sleep | 4 | 200ms | **800ms** | 循环 | ✅ 慢呼吸 |
| collapsed | 3 | 200ms | **600ms** | 循环 | 一般 |
| happy | 4 | 100ms | **400ms** | 单次 | ❌ 起跳+落地挤在 400ms |
| thinking | 3 | 120ms | **360ms** | 循环 | ❌ 歪头一闪 |
| sad | 3 | 120ms | **360ms** | 循环 | ❌ 下沉一闪 |
| wake | 4 | 80ms | **320ms** | 单次 | ❌ 最快 |
| alert | 3 | 100ms | **300ms** | 循环 | ❌ 几乎不可见 |

**第一条结论**：`idle` 之所以有效果，是因为它**恰好符合慢节奏**（600ms 且循环往复）；其余动作要么总时长只有 300~400ms，要么是一次性播放，人眼来不及形成"动作"印象。

人眼对"一个完整动作"的舒适感知区间约为 **600~1000ms**。低于 400ms 的动作，会被感知为"抖了一下"而不是"做了一件事"。

### 1.2 五条根因（按影响从大到小）

**R1 · 单次动作总时长不足**（主因，解决成本最低）
`happy` 400ms、`thinking` 360ms、`wake` 320ms、`alert` 300ms。都低于感知阈值。

**R2 · 每帧时长相同，没有节奏曲线**
每个情绪内部所有帧共用**同一个**间隔值 → 动作是"匀速位移"，缺少真动作的
*anticipation（预备）→ action（发力）→ settle（回落）* 三段速度变化。
对照 `pet4claude`：`idle: [280,110,110,140,140,320]` —— **每帧独立时长**，中间帧密集（快速动作）、首尾帧长（停顿）。

**R3 · 幅度受单图约束**
512 画布 → 256 窗口（×0.5）。`happy` 的 `-46px` 实际只有 **23px**；主体高 440→220px，即位移仅为主体高度的 **10%**。

**R4 · 特效与动作在抢时间**（`happy` 尤其明显）
`ui/pet_fx.py:101` 的 `happy` 爱心粒子 `interval=0.45s`、`life=1.2~1.9s`；
但 `happy` 单次动作只有 **400ms** → 粒子最多生成 1 个、还没升起来就切回 `idle`。
`EMOTION_EFFECTS` 目前只登记了 **sleep / happy / sad / alert** 四个情绪（`ui/pet_fx.py:95`），
其余情绪无特效。

**R5 · 姿态不变**
单图微变换只能做位移/缩放/旋转。"开心"的核心视觉载体是**耳朵/眼睛/尾巴**，这些单图变换动不了——
这是技术路线的**表达力天花板**，不是参数问题。

### 1.3 一句话总结

> 不是"间隔没配"，而是**动作太短、节奏太匀、幅度太小、特效来不及、姿态不变**。
> 前三条是**纯代码问题**（今天就能改），第五条需要补素材（成本最高）。

## 三、落地方案

### 方案 1 · 逐帧时长 + 节奏曲线（解决 R1 R2）⭐ 最高性价比 ✅ 已实施（2026-11-10）

**现状**：`EMOTION_INTERVALS[emotion] = 单个数值`，每帧共用。

**目标**：改为**时长数组**，并让单次动作总时长落在 600~1000ms。

```python
# ui/floating_pet.py
#: 情绪 → 每帧时长（毫秒）。数组长度应与该情绪的帧数一致；
#: 长度不足时回退到 FRAME_INTERVAL_FALLBACK。
EMOTION_FRAME_MS = {
    # 呼吸：慢—略快—慢，首尾留停顿
    "idle":      [260, 140, 140, 260],
    "sleep":     [420, 260, 260, 420],
    # 伸懒腰：预备(长) → 发力(短) → 舒展 → 回落(长)
    "wake":      [220, 90, 260, 320],
    # 歪头：慢起 → 停住
    "thinking":  [260, 200, 340],
    # 下沉：慢落
    "sad":       [220, 220, 320],
    # 跳跃：蓄力(长) → 起跳(极短) → 滞空(长) → 落地(短)
    "happy":     [180, 70, 320, 140],
    # 警觉：突然竖起 → 保持
    "alert":     [120, 140, 320],
    # 瘫下：逐渐失去力气
    "collapsed": [300, 280, 380],
}
FRAME_INTERVAL_FALLBACK = 150
```

接入方式：`_advance_frame()` 里把 `setInterval(interval)` 改为取**当前帧索引**对应的时长：

```python
durations = EMOTION_FRAME_MS.get(self._emotion)
if durations:
    idx = min(self._frame_idx, len(durations) - 1)
    self._anim_timer.setInterval(durations[idx])
else:
    self._anim_timer.setInterval(FRAME_INTERVAL_FALLBACK)
```

> 注意顺序：`setInterval` 必须在**推进帧索引之后**调用，否则会用上一帧的时长。

**预期收益**：`happy` 400→710ms、`thinking` 360→800ms、`wake` 320→890ms、`alert` 300→580ms。

**实施结果（2026-11-10，已落地并实测）**：

| 情绪 | 原总时长 | 现总时长 | 说明 |
|---|---|---|---|
| happy | 400ms | **710ms** | 蓄力 180 → 起跳 70（最快）→ 滞空 320（最慢）→ 落地 140 |
| thinking | 360ms | **800ms** | 慢起 260 → 过渡 200 → 停住 340 |
| wake | 320ms | **890ms** | 预备 220 → 发力 90 → 舒展 260 → 回落 320 |
| alert | 300ms | **580ms** | 突然竖起 120 → 140 → 保持 320 |

同时修掉一个**原有缺陷**：`set_emotion()` 重置了帧索引却没重设定时器间隔，
导致切换情绪后的**第一帧会沿用上一个情绪的时长**（如 idle 260ms → happy 本该 180ms）。
现已在 `set_emotion()` 内立即应用新情绪首帧时长。

守护测试：`tests/unit/test_frame_norm.py::TestFrameDurations` 6 项 ——
含"配置项数必须等于素材帧数"（素材重生成后帧数变化而配置没跟，动作会被截断或循环错位）。
**成本**：0.5 天（含单测）。
**验收**：真机上能一眼说出"它在跳/在歪头"。

### 方案 2 · squash & stretch 形变（解决 R3）✅ 已实施（2026-11-10）

**现状**：`tools/gen_pet_frames.py` 的变换只支持 `dy` / `scale_y` / `angle`。

**目标**：补齐动画十二原则里的**挤压拉伸**与倾斜：

- `scale_x`（与 `scale_y` 反向配合 = 体积守恒的 squash & stretch）
- `shear`（倾斜，表达奔跑/被拽）
- `anchor`（变换锚点：底部/中心，避免缩放时"飘起来"）

`happy` 的一种写法（蓄力→起跳→滞空→落地）：

```python
"happy": [
    {"dy": 0,  "scale_y": 0.92, "scale_x": 1.06},   # 蓄力：压扁
    {"dy": -30, "scale_y": 1.10, "scale_x": 0.94},  # 起跳：拉长
    {"dy": -48, "scale_y": 1.00, "scale_x": 1.00},  # 滞空
    {"dy": -6,  "scale_y": 0.94, "scale_x": 1.04},  # 落地：再压一下
]
```

**成本**：1 天（工具 + 规则 + 重新生成 + 渲染核对）。
**验收**：静止帧对比时，能看出"体积变化"而不只是"整体平移"。

**实施结果（2026-11-10，已落地并在渲染图上确认）**：

先解决了一个**空间约束**：画布 512、底部基线 491，主体 440 时向上只剩 51px；
而"拉长 1.08 倍 + 上移 34px"组合需要约 72px → **会顶出画布被裁切**。
故 `SUBJECT_HEIGHT` 由 `0.86` 降到 **`0.78`**（440 → 400），向上留 91px。
代价：桌宠整体在窗口内缩小约 9%（显示尺寸仍可用 `set_pet_size` 调整）。

改动：

| 项 | 改动 |
|---|---|
| `transform()` | 新增 `scale_x` 支持；与 `scale_y` 同时给即构成 **squash & stretch**（压扁时变宽、拉长时变窄，视觉体积守恒） |
| `SUBJECT_HEIGHT` | `0.86` → `0.78`（腾出向上空间，见上） |
| `EMOTION_RULES` | `happy` 重写为 蓄力压扁(0.90/1.07) → 起跳拉长(1.08/0.94) → 滞空 → 落地再压(0.93/1.05)；`wake` 先缩后伸展(0.95→1.10)；`collapsed` 压扁摊开(0.90/1.05)；其余情绪加极轻微纵向形变 |

未做：`shear`（倾斜）与 `anchor`（变换锚点）—— 前者在像素风格下容易糊边，
后者当前"底部对齐"已隐含满足需求，暂不引入。

守护测试（`tests/unit/test_gen_pet_frames.py` 9 项）：

- `scale_x` 只改宽度；压扁=更宽更矮；拉长=更窄更高；旋转不改尺寸；
- **`test_every_frame_stays_inside_canvas`**：遍历所有情绪的每一帧，断言内容 bbox
  **不贴画布边缘**（即未被裁切）—— 这条最实用，参数调大一点就会把猫头顶切掉，
  而缩略图里不容易发现；
- 底部基线对齐；规则键名白名单（拼错的键会被静默忽略）；
- `happy` 必须同时含压扁帧与拉长帧（否则退化成整体平移）。

**验收（渲染图已确认）**：`happy` 第 1 帧明显横向变宽、纵向压矮；第 2 帧拉长；
第 4 帧落地再压。**待真机确认**动起来的感觉。

### 方案 3 · 特效与动作时长对齐（解决 R4）✅ 已实施（2026-11-10）

**问题**：`happy` 动作 400ms，而爱心粒子 `interval=0.45s` 才发第 1 个。

**改法**（二选一或并用）：

1. 缩短首发作间隔：`happy.interval` 0.45 → 0.25，并把 `life` 下限从 1.2 降到 0.9，
   让粒子在动作结束前就可见；
2. 让**粒子寿命跨状态存活**：`set_emotion` 切换时**不清空已有粒子**（只停止发射），
   这样回到 `idle` 后爱心还能飘完 —— 视觉上"动作结束但情绪残留"，这正是桌宠该有的味道。

> 当前 `ui/pet_fx.py` 的 `set_emotion()` 会重置发射状态；需确认是否清空 `_particles`（未核实，实施时先查）。

**实施结果（2026-11-10，已落地并实测）**：

核实结论：`set_emotion()` **确实会 `self._particles.clear()`**；而 `advance()` 中
「粒子推进与回收」在「读取情绪特效配置」**之前**执行 —— 所以只要不在切换时清空，
旧粒子就会自然飘完，无需改 `advance()`。

改动：

| 项 | 改动 |
|---|---|
| `set_emotion()` | **不再清空粒子**，只换发射器并重置发射计时（数量仍受 `MAX_PARTICLES` 约束） |
| `happy` interval | 0.45 → **0.22**（710ms 动作窗口内约发 3 个） |
| `wake` interval | 0.7 → **0.28**（890ms 内约 3 个） |
| `alert` interval | 0.55 → **0.28**（580ms 循环内约 2 个） |
| `thinking` interval | 1.1 → **0.45**（原值 1.1s **大于** 800ms 循环，一个都发不出） |
| `sad` interval | 0.8 → **0.40** |
| `sleep` interval | 保持 1.5（慢呼吸配 Zzz，本就该慢） |

守护测试（`tests/unit/test_pet_fx.py`）：
- `test_set_emotion_keeps_particles` —— 切换后粒子数不变（原测试断言"清空"，已随设计变更改写）；
- `test_old_particles_fade_after_switching_to_plain_emotion` —— 切到 idle 后旧粒子仍会飘完并回收；
- `test_emission_interval_fits_action_duration` —— **发射间隔不得大于动作窗口**（单次动作按 1 个循环算，循环情绪按 2 个），防止新增情绪时配了发不出来的间隔。

**成本**：0.5 天。 **验收**：`happy` 时能看到至少 2~3 个爱心飘起（**待真机确认**）。

### 方案 4 · 补姿态图（解决 R5，表达力质变）

**做法**：为 3 个关键情绪各生成 **2~3 张不同姿态**（如 `happy` 的"闭眼笑"、`sad` 的"垂耳"），
帧序列 = 姿态切换 + 微变换。生成后用 **centroid alignment**（借鉴 #9）对齐，避免重现
"AI 逐帧不一致"的老问题。

**成本**：2~3 天（含素材生成、对齐、效果核对）。
**风险**：素材仍是 AI 生成，虽经对齐，但姿态间的"神似"需人工把关。
**建议**：**放在方案 1~3 验收之后**再决定要不要做 —— 如果 1~3 已能让人"看懂",就不必付这个成本。

### 方案 5 · 状态机与行为调度（结构性改造，借鉴 #2 #5 #6）🟡 部分实施（2026-11-10：仅拖拽反馈）

**现状**：情绪由 `set_emotion(emotion, loop, after)` 直接切换，随机动作与情绪共用一条通道；
没有"拖拽优先"、"单次动作不被打断"、"切换需合法"的约束。

**目标**：

- 三层仲裁：`drag > oneshot > base`（`pet4claude`）；
- 合法转移图：如 `sleep` 不能直接跳 `happy`，须经 `wake`；
- 行为限流：同一动作在 N 秒内不重复（`PixelPal` 的 `BehaviorRateLimiter`）。

**成本**：2 天（新增 `ui/pet_state.py` + 改造 `set_emotion` 调用点 + 单测）。

**已实施部分（2026-11-10）—— 只做了"拖拽反馈"，未上三层状态机**：

核实发现：`set_emotion()` 的 6 个调用点（微动作 / 抚摸 / 动作回落 / 入睡 / 唤醒）
**没有一个与拖拽相关** → 拖拽时桌宠毫无反馈，仍显示 idle 呼吸，"被抓起来"这件事
在视觉上完全不存在。这比"动作被打断"更贴近实际体验缺口，故先补这一块：

| 改动 | 内容 |
|---|---|
| 新情绪 `drag` | `EMOTION_RULES` 加 3 帧：`angle ±6°` + `dy -2` + `scale_y 1.03`，循环播放 = 被拎着左右晃 |
| `KNOWN_EMOTIONS` | 加入 `"drag"`（自动纳入"素材必须存在""时长项数必须匹配"两条守护测试） |
| `EMOTION_FRAME_MS` | `"drag": [180, 200, 180]` |
| `mouseMoveEvent` | 移动距离 ≥ `_click_threshold`（5px）才切到 `drag`；**避免单击时猫"抽一下"** |
| `mouseReleaseEvent` | 若曾进入拖拽表现，回到 `idle` |

**仍未做**（原方案的主体）：

- 三层仲裁 `drag > oneshot > base` —— 目前拖拽会直接覆盖当前情绪（如 happy 播到一半被拖走就中断）；
- 合法转移图（`sleep` 不得直跳 `happy`，须经 `wake`）；
- 行为限流（`PixelPal` 的 `BehaviorRateLimiter`）。

这些属于结构改造，与"看得出动作"的观感无关，留待有实际需求时再做。
**依赖**：建议在方案 1~3 之后做，否则会把"看不出动作"和"状态调度错"两类问题混在一起。

## 六、风险与回滚

| 风险 | 应对 |
|---|---|
| 动作拉长后显得"拖沓" | 每帧时长集中在代码 `EMOTION_FRAME_MS`，单点可调；实测不满意可只改数值 |

| 特效跨状态存活导致粒子堆积 | `pet_fx` 已有 `MAX_PARTICLES = 24` 上限 |
| 素材改动不可逆 | `pet_png/` 由工具生成，删目录重跑即可还原；旧 `pet_svg/` 保留作为回退 |
