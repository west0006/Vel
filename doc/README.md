## 二、分层职责（按用途 · 按可信度）

**分层不是按主题分的，是按"能不能当依据"分的。** 越靠上越可信，越靠下变动越快：

| 层 | 性质 | 变动频率 | 可否作为开发依据 |
|---|---|---|---|
| `CURRENT-STATUS.md` | **现状快照**（在做什么 / 到哪了 / 有哪些问题） | 高（随时更新） | ✅ 判断"现在"的唯一依据 |
| `reference/` | **权威设计**：长期结论，会被反复引用 | 低 | ✅ 最高。修改须留修订记录，设计变更须先与用户确认 |
| `dev/` | **拿来干活的东西**：方案 / 计划 / 盘点 / 规格 | 高 | 🟡 方案类需看其**状态标记**；已实施或已作废的不再作数 |
| `knowledge/` | **按日期累积的调研**（含未定案与自我更正） | 一次性写入后基本不动 | 🟡 只作参考，不是规范 |
| `testing/` | 缺陷台账（一行一条 + 详情） | 随缺陷增减 | ✅ 描述"曾经坏了什么"的事实 |
| `历史对话/` | 对话存档 | 归档 | ❌ 仅追溯 |
| `归档/` | 被取代的旧文档 | 只增 | ❌ **不要据以开发**，仅供追溯决策链 |

> **一句话**：`dev/` 里的方案**不代表已经做了**；`reference/` 里的设计**不代表不会被改**；只有 `CURRENT-STATUS.md` 说"现在是什么样"。

### ★ 如何扩展（结构约定）

新增内容时按下表归入，**换主题只换文件名前缀，结构不变**：

| 要新增的内容 | 放哪 | 命名 |
|---|---|---|
| 权威设计（长期有效、会被反复引用） | `reference/` | `设计-<主题>.md` |
| 实施方案 / 待决方案 | `dev/` | `方案-<主题>.md` |
| 规格 / 标准（可自动化检验的硬性约束） | `dev/` | `规格-<主题>.md` |
| 盘点 / 评估（现状与差距分析） | `dev/` | `盘点-<主题>.md` / `评估-<主题>.md` |
| 计划与待办清单 | `dev/` | `计划-<主题>.md`（当前待办只有一份：`计划-当前待办.md`） |
| 当日执行记录 | `dev/日志/` | `YYYY-MM-DD.md`（**同日追加同一文件，不新建**） |
| 外部工具 / 技术调研 | `knowledge/` | `调研-<主题>.md`；按日期的调研用 `YYYY-MM-DD-<主题>.md` |
| 缺陷记录 | **一律合入** `testing/buglist.md` | **不新建文件** |
| 被取代的旧文档 | `归档/` | 必须先登记进 `归档/README-归档说明.md` |
| 对话存档 | `历史对话/` | `N.txt` |

## 四、时效性标记规范

**目的**：打开任意一份文档，就能立刻知道它还算不算数 —— 避免"照着已作废的方案开发"。

### 4.1 文件头必须写状态

每份 `dev/` 与 `reference/` 文档开头应有一行：

```markdown
> **状态**：✅ 现行 ｜ **最后核对**：2026-11-10
> **对应待办**：P1-2（可选）
> **机制来源**：某项目 `path/to/file.py::函数名`（MIT，仅借鉴设计未复制代码）
```

### 4.2 四种状态的含义

| 标记 | 含义 | 必须做的配套动作 |
|---|---|---|
| ✅ **现行** | 结论有效，可作为开发依据 | 结论变化时更新"最后核对"日期 |
| 🟡 **部分失效** | 部分章节已被取代 | 在文件头**明确写出**哪一节仍有效、哪一节已作废 |
| 📋 **未实施** | 方案已定但代码未做 | 实施后改成 ✅ 并更新 `CURRENT-STATUS.md`；若长期不做，说明原因 |
| ❌ **已取代** | 整体作废 | **必须移入 `归档/`** 并在 `归档/README-归档说明.md` 登记 |

### 4.3 引用外部项目时的写法

**写"文件 + 函数名/类名"，不要只写行号** —— 行号会随对方仓库更新而失准，函数名不会。

- ✅ `pet4claude` 的 `scripts/pet_daemon.py::AnimationSpec.current_duration_ms`
- ❌ `pet4claude` 的 `pet_daemon.py:154`

## 六、维护约定

1. **`reference/` 是权威层**：只放长期有效的结论。改动其中任何文件都必须在文件内留修订记录（版本号 + 日期 + 改了什么），设计层面的变更须先与用户确认。
2. **`CURRENT-STATUS.md` 必须随重大改动同步更新** —— 完成一个待办项、改变一个技术决策、出现一个新的阻塞，都要写进去。
3. **状态标记要与内容一致**：方案实施后改状态、作废后移归档、部分失效要写明哪部分还作数。**宁可标 🟡 也不要让读者自己猜。**
4. **按日期的文件同日追加，不新建**：`dev/日志/YYYY-MM-DD.md`、按日期的 `knowledge/` 调研文件。
5. **台账类一律合入既有文件**：缺陷进 `testing/buglist.md`，不新建单文件。
6. **归档不删除**：被取代的旧文档移入 `归档/` 并在 `归档/README-归档说明.md` 登记版本链与取代关系，归档件开头标注「⚠️ 已作废，不要据以开发」。
7. **不要在 `doc/` 放二进制大件**（图片、模型、exe）；需要引用素材时写路径。
8. **文档与代码的一致性由 Agent 负责**：Agent 每次任务开始前读 `README.md` + `CURRENT-STATUS.md`，任务结束前把结论沉淀到对应层，不允许只改代码不更新文档。
